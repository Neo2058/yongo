## Обновление существующей установки

1. Запланировать короткую остановку записи. Сделать резервную копию **БД и storage** и сохранить её вне сервера. Старый `yarn backup` сохранял только БД: отдельно скопировать storage до обновления.
2. Установить зависимости из lockfile: `yarn install --immutable`. Нужен Node 22.18+ для тестового harness; production Docker использует Node 22.
3. Выполнить `yarn lint`, `yarn test:security`, `yarn build`, `yarn test:production`. `yarn build` использует поддерживаемый Webpack; повторную оценку Turbopack проводить отдельно.
4. Установить production `SITE_URL=https://ваш-домен`. Перед первой инициализацией задать уникальный пароль владельца длиной 12–256 символов. **Существующий пароль изменение env не обновляет.**
5. Поставить обновлённый контейнер. При первом обращении DAL автоматически создаёт новые служебные таблицы и однократно ограничивает старые бессрочные неиспользованные инвайты семью днями от миграции. Уже истёкшие ссылки не продлеваются. Принятые доступы не ограничиваются этим сроком.
6. Проверить сценарии доступа через HTTPS. Старые public uploads черновиков теперь будут недоступны анониму; в опубликованном контенте сохранятся.
7. Очистить прежний CDN/reverse-proxy/image cache, если он использовался для `/media/**` или `/_next/image`. Старые ответы имели годовой immutable-кеш. Уже сохранённые посетителями копии файлов отозвать невозможно.

Миграция не удаляет статьи, заявки, заказы, файлы и пользователей. Второй владелец, если он уже был создан старым bootstrap, автоматически не удаляется: проверить список owner-аккаунтов вручную. Слабые существующие пароли тоже автоматически не заменяются — сменить их отдельно.

## Прокси и сеть

В репозитории есть `deploy/nginx/yongo.conf.example` и `deploy/nginx/yongo-proxy.conf`. Пример рассчитан на Nginx на том же VPS, прямой доступ пользователей и контейнер на loopback. Он не установлен автоматически.

- Заменить `example.com`, пути сертификатов; скопировать proxy snippet в `/etc/nginx/snippets/yongo-proxy.conf` и проверить `nginx -t` перед reload.
- Сначала выпустить сертификат и настроить продление. Пример предполагает уже существующий сертификат.
- Установить `TRUST_PROXY=1` **только после** закрытия прямого доступа и установки proxy, перезаписывающего `X-Real-IP`. При `0`/отсутствии настройки приложение использует общий безопасный bucket; посетители будут разделять лимит.
- Разрешить извне только HTTPS, HTTP для перенаправления/сертификата и ограниченный SSH. Проверить, что порт 3000 недоступен извне.
- Если перед Nginx стоит CDN, настроить real-IP module только для официальных диапазонов CDN; не доверять произвольному forwarded header. Иначе все пользователи CDN делят один IP-лимит.
- Пример не кеширует ответы приложения и ограничивает POST и общий поток запросов. Большой multipart допускается только на административных маршрутах. Не включать общий proxy_cache для личных страниц/RSC/медиа.
- Не сохранять полные URL приглашений в access log, аналитике, APM и error tracking. В примере access log для `/i/` отключён; дополнительно проверить журналы ошибок и внешние сервисы.
- HSTS добавляется на HTTPS-прокси; не объявлять его до исправной работы TLS.

## Смена пароля владельца

На локальной установке:

```bash
yarn owner:password owner@example.com
```

В контейнере (пароль вводится скрыто; не передавать его аргументом или env):

```bash
docker compose exec web node scripts/owner-password.mjs owner@example.com
```

Скрипт меняет только существующего активного owner, сначала сохраняет копию БД, затем в одной транзакции меняет пароль и отзывает его сессии. Для восстановления доступа понадобится доступ к серверу. Обновить или убрать bootstrap-секреты из env после смены; сам скрипт их не переписывает. Копии перед сменой пароля содержат старые хеши, хранить их приватно; они не входят в автоматическую ротацию обычных snapshots.

## Резервные копии и восстановление

```bash
yarn backup
# В production-контейнере:
docker compose exec -T web node scripts/backup-sqlite.mjs
```

По умолчанию снимок создаётся в `data/backups/<UTC timestamp>/`, хранится 7 завершённых снимков. `BACKUP_DIR` задаёт другой каталог, `BACKUP_KEEP` — положительное число снимков. Ротация удаляет только завершённые каталоги формата `yongo-backup-v1`; старые `.sqlite` и неизвестные файлы остаются. Директории и файлы создаются с приватной umask; отдельно ограничить права уже существующих каталогов и `.env.local`.

Uploads создаются под новыми именами и не перезаписываются; БД снимается перед копированием storage. Существующие ссылки snapshot поэтому находят свои файлы, а лишние новые файлы без записи в снимке не влияют на восстановление. Во время ручной очистки storage остановить запись/удаление. Симлинки в storage запрещены при backup.

Настроить cron/systemd timer на ежедневный запуск, уведомление при ненулевом коде, **шифрованную копию вне VPS** с отдельными ключами доступа. Настройка внешнего хранилища остаётся задачей владельца инфраструктуры: адрес и учётные данные не заданы.

Проверка восстановления на отдельной установке:

1. Остановить тестовое приложение; создать пустые `data/` и `storage/`.
2. Скопировать snapshot `yongo.sqlite` в `data/yongo.sqlite`, содержимое snapshot `storage/` — в `storage/`. Не смешивать с существующими WAL/SHM-файлами другой БД.
3. Назначить владельца каталогов UID/GID контейнера `1001:1001`, приватные права.
4. Запустить ту же версию приложения; проверить вход, записи CRM и public/internal медиа. Отозвать восстановленные сессии, если это аварийное восстановление после инцидента.
5. Зафиксировать дату, выбранный snapshot и результат. Проверять восстановление регулярно; успешное копирование само по себе его не доказывает.

Результаты на 2026-10-09:

- `yarn build` — production Webpack-сборка успешна, все маршруты созданы. Локальные шрифты исключили зависимость от Google Fonts. Turbopack в этом окружении не завершал компиляцию; Webpack выбран явно, а не как скрытая подмена теста.

- `yarn npm audit --environment production --recursive --no-deprecations --json` — exit 0, известных advisory не найдено. `--no-deprecations` исключает сообщения о deprecated-пакетах, не CVE/advisories.
- Полный audit всех зависимостей — один известный High: **braces 3.0.3 / GHSA-vfj7-8cjw-p6xm**. Он приходит только через `@next/eslint-plugin-next → fast-glob → micromatch`, не входит в standalone и не обрабатывает пользовательские запросы. [Upstream advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) указывает, что исправленной версии нет. Не принимать недоверенные glob-паттерны в инструментах сборки; обновить пакет, как только выйдет патч. CI допускает только этот конкретный отчёт/версию/цепочку, не любые будущие уязвимости. Поддержка ESLint 9 и совместимость plugin peer dependencies требуют отдельного будущего обновления; deprecated-сообщение также остаётся видимым в audit без этого флага.
