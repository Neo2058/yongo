# План разработки: портфолио + закрытый рабочий контур + CMS/CRM

Статус: зафиксирован 2026-08-26. Учебный `src/app/dashboard` **не изменять**, пока не закрыт шлюз фазы 0.

Этот документ — дорожная карта продукта. Реализация публичной части, скрытого контура и CMS/CRM начинается только после освоения основного стека Next.js 16. Учебный dashboard остаётся полигоном и позже станет каркасом админки.

---

## 1. Что строим

Сайт разработчика со стеком: React, Next.js, Nest.js, PHP, UE5, C++, 3ds Max, Blender, HTML/CSS/JS, Assembler, Linux/Windows, разворачивание сервера с нуля, Docker, GitHub, работа с агентом Grok.

Три поверхности одной системы:

| Поверхность | Кто видит | Зачем |
|---|---|---|
| Публичная | любой посетитель | работы, открытый блог, заявка, заказ работы/системы |
| Закрытая | только приглашённые руководители | рабочий блог / брифы / статус работ |
| Управление | только владелец (ты) | CMS + CRM: контент, заявки, заказы, доступы |

Тёмная тема и анимации — часть продукта, не «потом накрутим». CMS не отдельный блог-движок, а смесь с CRM и разделением каналов публикации.

## 2. Жёсткое ограничение по безопасности

Скрытый URL **не является защитой**. Ссылка утекает через историю браузера, Referer, скриншоты, логи прокси, пересылку в мессенджере, кэш, autocomplete. Краулеры и сканеры перебирают пути. `robots.txt` с `Disallow: /secret/` сам рекламирует секретный путь.

Закрытый контур строится **тремя слоями сразу**. Один слой без двух других считается дырой.

```
Слой A — невидимость
  нет пункта в публичном меню
  нет записи в sitemap
  не светить путь в robots.txt
  X-Robots-Tag: noindex, nofollow на ответах закрытого контура
  для постороннего тот же 404, что у несуществующей страницы

Слой B — вход только по приглашению
  ты генерируешь ссылку с непредсказуемым токеном и отправляешь человеку
  токен одноразово (или с коротким TTL) создаёт сессию / аккаунт руководителя
  дальше — обычный логин (magic link или пароль)
  cookie сессии: httpOnly, Secure, SameSite=Lax/Strict

Слой C — проверка на каждой операции
  proxy.ts может лишь рано отсечь «похоже, не залогинен»
  право читать/писать проверяется в Data Access Layer на сервере
  Server Action / Route Handler без проверки роли = обход UI
  в клиент уходит только DTO, без лишних полей
```

Правило продукта: **не знаешь ссылку → не видишь, что подсистема существует. Знаешь ссылку, но не приглашён → 404. Приглашён, но истёк доступ → 404 или экран «нет доступа» только после успешной аутентификации.** Не различаем «страница есть, но закрыта» и «страницы нет» для анонима. Иначе по ответу сервера сканируют скрытые маршруты.

## 3. Роли

| Роль | Как появляется | Права |
|---|---|---|
| `owner` | единственный аккаунт владельца | полный CMS/CRM, все каналы, инвайты, заказы |
| `manager` | только по твоей ссылке-приглашению | читать закрытый рабочий блог, оставлять комментарий (позже) |
| `visitor` | аноним | публичные страницы, заявка, заказ |
| `client` | позже, из принятого заказа | статус своего заказа, не чужие |

Публичной регистрации нет. Руководитель не может пригласить другого. Отзыв инвайта и сессий — обязательная операция в CRM.

## 5. Каналы контента (CMS) и сущности CRM

Одна запись контента. Не три блога и не три базы.

```
Content
  id, slug, title, body, cover
  channel:   public | internal | shop
  status:    draft | published | archived
  type:      article | case | service | briefing
  publishedAt, updatedAt
  authorId (owner)

Lead          заявка с /contact
Order         заказ с /services или /order
  status:     new | qualified | in_progress | delivered | closed | cancelled
Invite        токен, email/имя, role=manager, expiresAt, usedAt, revokedAt
Session       кто вошёл, lastSeen, revoke
AuditEvent    кто что открыл/изменил (минимум для закрытого блога)
```

Правила публикации:

- `channel=public` + `published` → открытый блог / кейс.
- `channel=internal` + `published` → только `owner` и `manager` с живой сессией.
- `channel=shop` + `published` → карточка услуги, её можно заказать.
- Черновик не существует для публики и для руководителя. DAL не отдаёт `draft` никому, кроме `owner`.

Заявка и заказ — CRM-сущности, не письма «в никуда». Письмо владельцу — побочный эффект, источник истины — запись в базе. Иначе заявка потеряется, если SMTP ляжет.

Оплата онлайн в v1 **не входит**. Заказ = заявка с составом работ и статусом в CRM. Платёжный шлюз — отдельная фаза: юридические обязательства, PCI, вебхуки, идемпотентность.

## 6. Стек и границы

Зафиксировано сейчас:

| Слой | Решение | Почему |
|---|---|---|
| UI и BFF | Next.js 16 App Router, React 19, TypeScript strict, Tailwind 4 | учим и показываем актуальный стек; этот репозиторий уже на нём |
| Данные | PostgreSQL + DAL на сервере (`server-only`) | для нового Next-проекта это рекомендуемый путь; права в одном месте |
| Скрытый контур | invite token + сессия, не «секретный path» | см. §2 |
| Админка | позже эволюция `/dashboard` | ты сам связал учебный dashboard с будущей CMS |
| Деплой | Docker + Linux с нуля | это часть позиционирования |
| Тема | тёмная по умолчанию, светлая как опция, `prefers-color-scheme` | требование продукта |
| Движение | CSS + точечные клиентские анимации, уважение `prefers-reduced-motion` | анимация не должна ломать a11y и Core Web Vitals |

Явно не смешивать в этом приложении:

- PHP как второй бэкенд этого сайта. PHP остаётся навыком в портфолио, не рантаймом CMS.
- Три ORM / две CMS / Headless «на всякий случай».
- Auth только в `proxy.ts`. Документация Next 16 прямо говорит: proxy — ранний отсев, не полноценная авторизация.

Nest.js: **не в фазе 1**. Сначала контент и формы на Next.js + DAL. Когда CRM (воронка заказов, вебхуки, очереди писем, фоновые джобы) станет тесной в Server Actions — выносим домен заказов/инвайтов в Nest.js как внутренний API, Next остаётся UI и BFF. Это покажет оба стека без двойной работы на старте.

## 8. Фазы

Каждая фаза имеет **шлюз**: пока он не закрыт, следующую не начинаем. Шлюз — не «страница открывается», а список фактов, которые можно проверить.

### Фаза 0 — освоение Next.js 16 (сейчас)

Полигон: текущий `src/app/dashboard` и учебные маршруты. Продуктовые страницы не пишем.

Освоить и уметь объяснить на пальцах:

1. Дерево App Router: `layout` / `template` / `page` / `loading` / `error` / `not-found`.
2. Почему layout держит state, а template сбрасывает; зачем `key` у template.
3. Server vs Client Components: где граница `'use client'`, почему нельзя класть её на весь layout продукта.
4. Dynamic route `params` как `Promise` (это Next 16, не «как в старых гайдах»).
5. `error.tsx`: Client Component, в проде не светить сырой `error.message` с сервера, retry через `unstable_retry`.
6. Навигация `Link`, prefetch, когда он вреден.
7. Fetch на сервере, мутации через Server Actions, валидация на сервере.
8. `proxy.ts` вместо deprecated `middleware`.
9. Metadata, `lang`, шрифты с нужным subset (для ru — кириллица).
10. Образы через `next/image`, не сырой `<img>` для контента.

Шлюз фазы 0: ты без подсказки объясняешь разницу layout/template, ставишь `'use client'` только там, где нужен state, и понимаешь, что params — Promise. После этого — рефакторинг dashboard в админку, не раньше.

Параллельно (можно читать, не кодить продукт): этот план, гайды Next 16 `authentication`, `data-security`, `forms`, `content-security-policy`.

### Фаза 1 — каркас продукта рядом с учебным кодом

Не ломая dashboard:

- route groups для публичной части;
- корневые metadata, `lang`, шрифт с `cyrillic`;
- тёмная тема (класс на `<html>`, CSS-переменные);
- security headers (CSP с nonce через `proxy.ts`, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`);
- ESLint, скрипт `lint`, базовый `.env.example` без секретов;
- публичный 404 без фразы «возможно, нет доступа».

Шлюз: `yarn lint` и `yarn build` зелёные, тема переключается, заголовки видны в ответе, `/dashboard` учебный жив.

### Фаза 2 — публичное портфолио

- `/`, `/work`, `/work/[slug]`;
- контент кейсов сначала можно держать типизированными файлами, не CMS;
- стек и навыки как данные, не как простыня в JSX;
- анимации появления секций с `prefers-reduced-motion`.

Шлюз: набор кейсов открывается, SEO title/description на каждой, изображения не прыгают (нет лишнего CLS).

### Фаза 3 — открытый блог + заявка + заказ без оплаты

- `/blog`, `/blog/[slug]`;
- `/contact` и `/order` / `/services` как формы → Server Action → запись Lead/Order;
- валидация Zod (или аналог) **на сервере**;
- honeypot + rate limit + ограничение размера тела;
- письмо владельцу — после записи в БД, не вместо неё;
- никаких секретов SMTP в клиенте.

Шлюз: заявка с пустыми полями отвергается, флуд упирается в лимит, успешная заявка есть в БД даже если почта упала.

### Фаза 4 — приглашения и закрытый блог руководителей

Это самая опасная фаза. Порядок обязательный:

1. Модель Invite + Session + AuditEvent.
2. Генерация токена криптостойким RNG (`crypto.randomBytes` / `randomUUID` + HMAC), энтропия не меньше ~128 бит. Не `Math.random()`, не короткий slug.
3. `/i/[token]`: погашение, затем сессия. Неверный/погашенный/отозванный токен → 404.
4. DAL: `getBriefingDTO` отдаёт тело **только** если роль `manager|owner` и `channel=internal` и `status=published`.
5. Не класть закрытые записи в sitemap, RSS, OG-кэш публичного CDN, поиск по сайту.
6. В CRM: список инвайтов, отзыв, принудительный logout всех сессий руководителя.
7. Лог: кто открыл какую запись (для тебя, не для публики).

Шлюз: человек без токена получает 404 на `/briefing` и на `/i/guess`. Человек с отозванным токеном — тоже 404. В RSC payload закрытой страницы нет полей, которых нет в DTO. Попытка вызвать Server Action чтения брифинга без сессии не возвращает данные.

### Фаза 5 — CMS/CRM в `/dashboard`

Эволюция учебного dashboard, не новый параллельный `/admin`, если не упрёмся в конфликт с учебными файлами.

Разделы:

- контент с фильтром канала `public | internal | shop`;
- публикация / снятие с публикации;
- заявки и заказы со сменой статуса;
- инвайты;
- нельзя «опубликовать internal как public» одной галочкой без явного смены канала.

Шлюз: owner публикует internal-запись — она не появляется в `/blog`. Owner отзывает инвайт — сессия руководителя умирает на следующем запросе.

### Фаза 6 — укрепление (по необходимости)

- Nest.js как домен заказов/очередей, если Server Actions начнут расползаться;
- онлайн-оплата;
- кабинет `client`;
- медиахранилище для роликов UE5/Blender (не `public/` для закрытых файлов);
- бэкапы Postgres, ротация секретов, CI с lint/test/audit.

## 9. Угрозы, которые будем ловить на каждой фазе

| Угроза | Где всплывает | Как закрываем |
|---|---|---|
| Security through obscurity | скрытый маршрут | §2, три слоя |
| IDOR | `/briefing/[slug]`, `/dashboard/orders/[id]` | DAL проверяет роль и владение, не UI |
| Утечка через RSC payload | передача объекта в Client Component | DTO + `server-only` + не прокидывать entity |
| XSS | MDX, комментарии, заявка в админке | не `dangerouslySetInnerHTML` на сыром вводе; санитайз; CSP |
| CSRF / чужой origin | Server Actions | проверка сессии внутри экшена; не полагаться на скрытую форму |
| Перебор инвайтов | `/i/[token]` | длинный токен, rate limit, одинаковый 404 |
| Спам заявок | `/contact`, `/order` | honeypot, rate limit, опционально challenge |
| Open redirect | `?next=` после логина | allowlist внутренних путей |
| SSRF через картинки | `next/image` remotePatterns | только свои хосты |
| Path traversal / file dump | загрузка медиа | свои имена файлов, вне web-root для internal |
| Перечисление пользователей | логин, инвайт | одинаковые ответы, без «email не найден» |
| Секрет в репозитории | `.env`, `NEXT_PUBLIC_*` | `.env*` уже в gitignore; публичный префикс = браузер |
| Clickjacking | любая страница | `frame-ancestors 'none'` |
| Индексация закрытого | sitemap/robots/OG | не включать, заголовок noindex, 404 анониму |

Ошибки не показывают внутренности. В `error.tsx` продукта — нейтральный текст + `digest` в логах, не `error.message`.

## 10. Тема и анимация — продуктовые правила

- Тёмная тема — default. Светлая — явное переключение, сохранение предпочтения.
- Токены цвета в одном месте (`src/theme` / CSS variables), запрет «захардкоженный `#000` в случайном компоненте».
- Анимация: вход героя, переход карточек работ, микро-состояния форм. Не анимировать layout админки ради эффекта.
- `prefers-reduced-motion: reduce` отключает движение.
- Не подключать тяжёлый 3D-движок на каждую страницу. UE5/Blender — в кейсах как видео/постеры, не как WebGL по умолчанию.

## 11. Как ведём проект с Grok

- Перед кодом на Next 16 — гайд в `node_modules/next/dist/docs/`, не память модели. В этой версии `middleware` → `proxy`, `params` — Promise, retry в error boundary — `unstable_retry`.
- Учебный `src/app/dashboard/**` не меняем до закрытия шлюза фазы 0. Исключение: ты явно просишь поправить учебный пример.
- Каждая новая поверхность (форма, динамический id, инвайт, загрузка файла) проходит короткий разбор угроз до реализации.
- Не добавляем библиотеку «на будущее». Auth-библиотека — да, когда дойдём до фазы 4, не в фазе 0.
- Проверка в браузере: не только скрин, а сценарий пользователя (отправка формы, 404, смена темы, попытка открыть `/briefing` без сессии).
- Этот файл обновляем, когда решение меняется. Старое решение не удаляем молча — строка в журнале ниже.
